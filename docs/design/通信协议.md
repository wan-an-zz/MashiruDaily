# MashiruDaily ⇄ Hermes 前后端通信协议

> 本文档落实 `前后端通信架构设计.canvas` 与 `前后端通信的托底设计.md` 两份设计文档，是 MashiruDaily 客户端与 Hermes/服务器同步功能的权威契约（Task C）。客户端实现（Task D）与本协议定义的服务端实现均以本文为准，实现时不得偏离本文规定的端点、字段、默认值与语义。

**状态说明**：

- **Webhook 推送（第 3 章）**：由客户端发起、Hermes 接收，Hermes 已内置 aiohttp Webhook 服务器，客户端按本文实现。
- **上线拉取的两个 GET 端点（第 5 章）**：为**本协议定义的服务端契约，服务端尚未实现**。客户端按本文契约实现调用逻辑，并在端点不可用时按第 5.4 节降级处理；服务端将来必须按本文实现这两个端点。

---

## 1. 系统拓扑

```
┌─────────────────────┐   Webhook 推送    ┌──────────────────────┐
│  MashiruDaily 客户端 │ ────────────────▶ │  Hermes              │
│  (Avalonia 桌面 /    │    POST :8644     │  (内置 aiohttp       │
│   Android / TUI，    │                    │   Webhook 服务器)     │
│   共用同一后端)       │                    │                      │
└─────────────────────┘                    └──────────┬───────────┘
        │   ▲                                          │ 工具操作
        │   │  REST 拉取                                ▼
        │   │  GET /api/todo/meta                ┌─────────────┐
        │   └─ GET /api/todo                     │ 服务器       │
        │        (本协议定义，                    │ todo.json   │
        │         服务端尚未实现)                  │ plan.md     │
        └───────────────────────────────────────▶└─────────────┘
        Hermes 通过 Time Trigger (hermes cron)
        定时提醒 Hermes 更新当日 Todo → todo.json
```

- **客户端**：Avalonia 桌面 / Android / TUI 三端共用同一后端（`TodoService` + `JsonTodoRepository`，数据落 `%APPDATA%\MashiruDaily\todos.json`），三端使用同一套同步实现。
- **Hermes**：AI 智能体运行时，内置 aiohttp Webhook 服务器，默认监听端口 `8644`。收到事件后通过工具操作服务器上的 `todo.json`（必要时同步 `plan.md`）。
- **服务器**：运行 Hermes 与数据文件的宿主机。`todo.json` 是服务器侧的唯一数据源，客户端不直接写服务器文件。
- **同步方向**：客户端 → Hermes 为 Webhook 事件推送；客户端 → 服务器为 REST 拉取（GET 只读，不修改服务器状态）；服务器 → 客户端的数据变更经由 Hermes 每日更新 `todo.json` 后，由客户端上线拉取生效。

## 2. 事件类型（5 种）

| type | 触发场景 | payload 说明 |
|---|---|---|
| `todo_added` | 新建待办 | 完整条目（`HasSynced` 不传输） |
| `todo_updated` | 修改标题；或重发历史待同步项（upsert 语义：`Id` 未知则创建，已知则更新） | 完整条目 |
| `todo_completed` | 标记完成 | 完整条目（`isCompleted=true`，`completedAt` 非空） |
| `todo_reopened` | 从完成重新打开 | 完整条目（`isCompleted=false`，`completedAt=null`） |
| `todo_deleted` | 删除待办 | 完整条目（删除前快照，Hermes 按 `id` 删除） |

规则说明：

- payload 一律为**完整条目**（快照），服务端（Hermes）不依赖增量字段即可重建/覆盖对应条目。
- `HasSynced` 是客户端本地字段，**任何事件类型都不得在 payload 中传输**。
- `todo_updated` 是 upsert 语义：Hermes 侧不存在该 `id` 时创建，存在时更新。客户端重发历史待同步项时也统一使用 `todo_updated`（见第 6 章）。
- `todo_deleted` 的 payload 是删除前的完整快照，Hermes 按 `id` 删除，不需要其他字段。

## 3. Webhook 推送（客户端 → Hermes）

### 3.1 端点

```
POST {HermesBaseUrl}/webhooks/{WebhookRouteName}
```

默认值：`HermesBaseUrl = http://<hermes-host>:8644`，`WebhookRouteName = todo-sync`。

即默认完整地址：

```
POST http://<hermes-host>:8644/webhooks/todo-sync
```

两个值均可在客户端设置中覆盖（用于多实例或非默认端口部署）。

### 3.2 请求头

| Header | 值 | 说明 |
|---|---|---|
| `Content-Type` | `application/json` | 固定值 |
| `X-Webhook-Timestamp` | 当前 Unix 秒（整数） | 服务端校验与自身时钟偏差 ±300 秒，超出拒绝（防重放） |
| `X-Webhook-Signature-V2` | 小写 hex 的 `HMAC-SHA256` 签名 | 计算方式见 3.3 |
| `X-Request-ID` | 事件 UUID | 幂等去重键，服务端按此去重（见 3.4） |

`X-Request-ID` 与事件体中的 `eventId` 为同一个 UUID，两者一致。

### 3.3 签名

```
signature = lowercase_hex( HMAC_SHA256( secret, "{timestamp}.{rawBody}" ) )
```

- `secret`：客户端设置中的 `WebhookSecret`，与 Hermes 路由配置 `secret` 必须一致（见 6.6）。
- `{timestamp}`：与 `X-Webhook-Timestamp` 头的值完全相同的字符串。
- `{rawBody}`：HTTP 请求体的**原始字节**（编码前），与 `Content-Type: application/json` 发送的字节完全一致。签名在序列化后对原始字节计算，**不得**对反序列化后重新序列化的 JSON 计算。
- 结果输出为小写十六进制字符串（64 个字符），放入 `X-Webhook-Signature-V2` 头。

### 3.4 幂等去重

- 服务端以 `X-Request-ID`（事件 UUID）作为去重键，TTL 为 **1 小时**。
- TTL 内收到相同 `X-Request-ID`：不重复触发 agent，响应 `200 {"status":"duplicate",...}`。
- 客户端对每个事件生成唯一的 `eventId`/`X-Request-ID`，重试同一事件时**复用同一个 UUID**（保证重试被幂等吸收）。

### 3.5 请求体（camelCase 字段名）

```json
{
  "type": "todo_completed",
  "clientId": "00000000-0000-0000-0000-000000000000",
  "eventId": "11111111-1111-1111-1111-111111111111",
  "timestamp": "2026-08-10T11:30:00+08:00",
  "payload": {
    "id": "22222222-2222-2222-2222-222222222222",
    "title": "买菜",
    "isCompleted": true,
    "createdAt": "2026-08-10T09:00:00+08:00",
    "completedAt": "2026-08-10T11:30:00+08:00"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | string | 事件类型，取第 2 章 5 个枚举值之一 |
| `clientId` | string (UUID) | 客户端实例标识（三端共用配置，每台设备一个） |
| `eventId` | string (UUID) | 事件唯一标识，与 `X-Request-ID` 一致 |
| `timestamp` | string (ISO 8601) | 事件发生时间，带时区偏移（如 `+08:00`） |
| `payload` | object | 完整条目快照，字段为 camelCase 的 `id`/`title`/`isCompleted`/`createdAt`/`completedAt`，不含 `HasSynced` |

payload 字段与本地 `TodoItem` 模型的对应关系：

| payload (camelCase) | 本地 todos.json (PascalCase) | 类型 |
|---|---|---|
| `id` | `Id` | string (UUID) |
| `title` | `Title` | string |
| `isCompleted` | `IsCompleted` | bool |
| `createdAt` | `CreatedAt` | string (ISO 8601，UTC+8 DateTime) |
| `completedAt` | `CompletedAt` | string (ISO 8601) 或 null |

### 3.6 响应判定（客户端逻辑）

| 响应 | 判定 | 客户端动作 |
|---|---|---|
| `202 {"status":"accepted",...}` | 成功（agent 模式，异步处理） | 条目 `HasSynced=true` |
| `200 {"status":"delivered",...}` | 成功 | 条目 `HasSynced=true` |
| `200 {"status":"duplicate",...}` | 成功（服务端已处理过本事件） | 条目 `HasSynced=true` |
| `200 {"status":"ignored",...}` | 成功（服务端有意忽略，如路由禁用但返回 200） | 条目 `HasSynced=true` |
| `401`（签名错误/缺失） | 失败 | 重试直至 `MaxRetryAttempts` |
| `403`（路由无 secret / 禁用） | 失败 | 重试直至 `MaxRetryAttempts` |
| `404`（路由不存在） | 失败 | 重试直至 `MaxRetryAttempts` |
| `400`（无法解析） | 失败 | 重试直至 `MaxRetryAttempts` |
| `413`（请求体超 1MB） | 失败 | 重试直至 `MaxRetryAttempts` |
| `429`（默认 30 次/分/路由限流） | 失败 | 退避约 2 秒后重试，直至 `MaxRetryAttempts` |
| 网络异常 / 超时（`TimeoutSeconds` 默认 10s） | 失败 | 重试直至 `MaxRetryAttempts` |

重试规则：

- `MaxRetryAttempts` 默认 **3**（即首次发送 + 最多 3 次重试）。
- 除 `429` 需按 2 秒退避外，其余失败可立即重试或采用短退避（建议 1 秒）。
- 重试耗尽仍失败：条目保持 `HasSynced=false`，客户端同步状态置为 `Error`，并提示用户手动同步（见第 6 章）。

## 4. 定时任务（服务端，Hermes cron / Time Trigger）

- 由 Hermes 的 cron 能力配置（例如 `0 9 * * *` 或 `every 1d`），周期性地提醒 Hermes 核对/更新 `todo.json`（必要时同步 `plan.md`）。
- 客户端**不参与**本流程，不感知定时任务的执行细节。
- 本协议记录该机制仅为保持系统拓扑完整；配置与实现属于服务端部署范畴，不在客户端契约内。
- 定时任务更新 `todo.json` 后，meta 的 `created_at`（见 5.1）随之变化，客户端下次上线即可感知并拉取。

## 5. 上线拉取（客户端 → 服务器，服务端契约）

> ⚠️ 本节的 **GET 端点为本协议定义、服务端尚未实现**。客户端按本文契约开发，并处理端点不可用（连接失败 / 非 200 / 解析失败）的情况——按第 5.4 节流程执行，失败时不覆盖本地数据。

### 5.1 GET {ServerBaseUrl}/api/todo/meta

请求：

```
GET {ServerBaseUrl}/api/todo/meta
```

`ServerBaseUrl` 默认与 `HermesBaseUrl` 相同（`http://<hermes-host>:8644`），可在设置中单独覆盖。

成功响应 `200`：

```json
{ "date": "2026-08-10", "created_at": "2026-08-10T17:00:00+08:00", "count": 12 }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `date` | string (yyyy-MM-dd) | 服务器 `todo.json` 的"当日日期"（Hermes 创建当日 Todo 的日期）；保留兼容返回，客户端判定改用 `created_at` |
| `created_at` | string (ISO 8601, UTC+8) | 服务器当前 `todo.json` 的创建时间（Hermes 定时任务每日生成当日 `todo.json` 的时刻），客户端判定是否拉取的主字段；不反映 Webhook 驱动的后续修改 |
| `count` | number | 服务器 `todo.json` 中条目数量 |

**`created_at` 语义声明**：

- `meta.created_at`（ISO 8601 UTC+8）表示服务器当前 `todo.json` 的**创建时间**：即 Hermes 通过定时任务（Time Trigger）每日生成当日 `todo.json` 的时刻。
- 它**不反映**之后经 Webhook 事件（客户端推送）触发的对 `todo.json` 的修改时间。若服务器用「最后修改时间」（如文件 mtime）作为该字段，则客户端每次 Webhook 推送后，下次启动都会因为服务器时间戳更新而判定「需要拉取」，造成每次 Webhook 同步后都重新拉取 todo.json 的无谓行为。
- 因此服务端实现必须：仅当 Time Trigger 重新生成 `todo.json` 时更新 `created_at`；Webhook 驱动的修改不得改变它。

### 5.2 GET {ServerBaseUrl}/api/todo

请求：

```
GET {ServerBaseUrl}/api/todo
```

成功响应 `200`，body 为 JSON **数组**，字段名为 snake_case（与服务器 `todo.json` 一致），**不含 `HasSynced`**（`HasSynced` 是客户端本地字段）：

```json
[
  {
    "id": "22222222-2222-2222-2222-222222222222",
    "title": "买菜",
    "is_completed": true,
    "created_at": "2026-08-10T09:00:00+08:00",
    "completed_at": "2026-08-10T11:30:00+08:00"
  }
]
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string (UUID) | 条目唯一标识 |
| `title` | string | 标题 |
| `is_completed` | bool | 是否已完成 |
| `created_at` | string (ISO 8601 UTC+8) | 创建时间 |
| `completed_at` | string (ISO 8601 UTC+8) 或 null | 完成时间，未完成时为 null |

### 5.3 客户端启动流程（meta 优先，拉取优先于推送）

客户端启动（或进入主界面）时按以下顺序执行，任一环节失败按 5.4 处理：

1. **加载设置**：读取同步设置（`SyncEnabled`、`HermesBaseUrl`、`WebhookRouteName`、`WebhookSecret`、`ServerBaseUrl`、`LastSyncedAt`、`MaxRetryAttempts`、`TimeoutSeconds`）。若 `SyncEnabled=false` 则**结束**，不进行任何网络操作。
2. **请求 meta 并解析 created_at**：`GET /api/todo/meta` → 解析 `created_at`（ISO 8601 UTC+8）。缺失或非法 → 同步状态置 `Error`，**不推不拉**。
3. **判定 needPull**：`LastSyncedAt` 为空或无法解析 → `needPull=true`；否则服务器 `created_at` **严格晚于** `LastSyncedAt`（相等视为本地最新）→ `needPull=true`。
4. **需拉取 → 跳过推送，直接覆盖**：`GET /api/todo` → 用返回数组**整体替换**本地列表（服务器为权威，本地原有但服务器不存在的条目会被删除，本地 `HasSynced=false` 的条目不推送即被覆盖丢弃）→ 全部条目置 `HasSynced=true` → 将 `LastSyncedAt` 持久化为服务器 `created_at`（规范化 ISO 8601 UTC+8）。
5. **无需拉取 → 推送待同步项**：将本地所有 `HasSynced=false` 的条目统一按 `todo_updated`（upsert 语义）逐个 POST 推送（顺序发送，见 6.4）。成功者置 `HasSynced=true` 并持久化。

### 5.4 语义与降级

- 拉取是**整列表覆盖**语义：一旦执行第 4 步，本地列表与服务器完全一致，本地原有但服务器不存在的条目会被删除。
- **拉取优先于推送**：判定需拉取时，本地 `HasSynced=false` 的条目不推送，且会被服务器整列表覆盖丢弃（服务器为权威）。
- 若 meta 或 todo 请求失败（网络异常 / 非 200 / 解析失败）：同步状态置 `Error`，**不覆盖本地数据**，保留 `LastSyncedAt` 原值，提示用户可稍后或手动同步（见 6.2）。
- Hermes 每日更新 `todo.json` 后 `created_at` 变化，客户端下次上线即可拉取当日 Todo。

## 6. 客户端行为规范

### 6.1 HasSynced 语义（托底设计）

- `HasSynced` 是客户端本地条目字段，仅存在于本地 `todos.json`，**不传输**。
- 以下操作后将条目置 `HasSynced=false`：新建（`todo_added`）、状态变更（完成/重新打开）、标题修改。
- Webhook 返回 OK（200/202，见 3.6）后置 `HasSynced=true` 并持久化。
- 正常与失败路径都只发送 `HasSynced=false` 的条目；`HasSynced=true` 的条目永不重发。
- 服务器对 `todo_updated` 的 upsert 语义保证：即使客户端重发历史条目，结果也是幂等的（已知则更新，未知则创建）。

### 6.2 手动同步

- 设置页提供**"立即同步"**按钮。
- 点击后：先 `GET /api/todo/meta` 比对 `created_at` 与本地 `LastSyncedAt`，判定需拉取则直接拉取覆盖（见 5.3 第 4 步）；否则推送本地 `HasSynced=false` 条目（`todo_updated` upsert）。
- 用于用户在同步失败（`Error` 状态）后主动恢复同步。

### 6.3 退出冲刷

- 应用退出前**尽力冲刷**尚未完成的推送：把 `HasSynced=false` 的条目依次 POST 一次。
- 冲刷**不无限重试**：只按 `MaxRetryAttempts` 正常重试，退出流程不因网络失败而阻塞。
- 冲刷失败的条目保持 `HasSynced=false`，下次启动自动重推。

### 6.4 限流

- 客户端**顺序发送**：同一时刻只有一个 POST 在途（不并发扇出），逐条等待响应后再发下一条。
- 目的：避免触发 Hermes 默认 **30 次/分/路由** 的限流（`429`）。
- 收到 `429` 时退避约 2 秒再重试（见 3.6）。

### 6.5 数据迁移

- 旧版本 `todos.json` 无 `HasSynced` 字段，反序列化时默认 `false`。
- 因此首次启用同步时，本地全部历史条目都会被判定为 pending → 全量推送一次。
- 这是**期望行为**：服务器获得完整数据（配合 `todo_updated` 的 upsert 语义，旧条目若已存在于服务器则更新，不存在则创建）。

### 6.6 Hermes 侧配置示例

写入协议文档，供服务端部署参考（Hermes 配置为 yaml 格式；`<与客户端 WebhookSecret 一致>` 处替换为与客户端 `WebhookSecret` 相同的值）：

```yaml
platforms:
  webhook:
    enabled: true
    extra:
      port: 8644
      routes:
        todo-sync:
          events: ["todo_added", "todo_updated", "todo_completed", "todo_reopened", "todo_deleted"]
          secret: "<与客户端 WebhookSecret 一致>"
          prompt: |
            收到 Todo 变更事件 {__raw__}
            请根据事件更新服务器上的 todo.json（必要时同步 plan.md）。
```

- `port: 8644` 与客户端默认 `HermesBaseUrl` 端口一致。
- `routes.todo-sync` 与客户端默认 `WebhookRouteName=todo-sync` 一致。
- `events` 列表覆盖第 2 章全部 5 种事件类型。
- `secret` 必须与客户端设置的 `WebhookSecret` 一致，否则签名校验失败（客户端收到 `401`）。
- 服务端 GET 端点（第 5 章）与本 Hermes 配置**相互独立**：GET 端点是本协议定义的、尚未实现的服务器 HTTP 服务；Hermes Webhook 配置仅服务于事件推送。
